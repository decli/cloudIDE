# POC 验证结果

> 2026-09-19。代码在 [`../poc/`](../poc/)，这里记录实测数据和暴露出来的问题。

## 1. 这次验证了什么

一条命令走完：一句话需求 → 生成并锁定验收测试 → 断网沙箱里写码自测 → 推到本地 Gitea → Gitea Actions 跑 CI → 制品发到 Release。

| 环节 | 选择 | 说明 |
|---|---|---|
| 模型 | DeepSeek `deepseek-flash` | OpenAI 兼容协议，function calling 正常 |
| 沙箱 | 本地 Docker，每任务一个容器 | `--network none`，2 CPU / 2G 内存 |
| 代码托管与 CI | 本地 Gitea + Gitea Actions | 两个容器，几百 MB 内存 |
| 黄金路径 | Python CLI 工具 + pytest | 制品是 zipapp 打出来的 `.pyz` |

**为什么没用 GitLab**：GitLab CE 自建要 4GB 内存起步、首次启动好几分钟，而这次只需要验证"推送触发 CI、CI 再发布制品"。Gitea 加 runner 一共两个容器就够，workflow 语法和 GitHub Actions 兼容，以后迁到 GitHub 或 GitLab 改动都不大。企业私有化场景另说，那时 GitLab 才有意义。

## 2. 实测数据

三个任务，都是一次通过，没用上修复轮：

| 任务 | 轮次 | 模型调用 | 输入 token（缓存命中） | 输出 token | 成本 | 结果 |
|---|---|---|---|---|---|---|
| 文本词频统计 | 1 | 10 | 37.7k（33.2k） | 5.4k | $0.0040 | 三项检查全绿 |
| JSON 格式化与校验 | 1 | 10 | 41.4k（37.9k） | 7.2k | $0.0049 | 全绿，CI 通过，制品已发布 |
| CSV 转 JSON | 1 | 8 | 27.1k（23.7k） | 4.7k | $0.0034 | 全绿，CI 通过，制品已发布 |

观察：

- **单任务成本在半分钱量级**。按这个价格，跑一个 30 条样本的评测集大约一毛多钱，成本完全不构成障碍。这也说明[可行性评估](02-feasibility.md)里按前沿模型算的 $5–30 单项目成本，换成国产模型能降两个数量级——前提是成功率跟得上。
- **缓存命中率约 87%**。agent 每轮都重发完整上下文，但命中缓存的部分单价只有 miss 的 1/50，所以实际花费远低于按 token 数的直觉估算。这印证了方案里"提示缓存是最大的一个降本手段"。
- **三个任务都一轮通过**，说明这个难度对模型来说太简单了，不足以暴露"最后 20%"问题。下一步必须加难度，否则测出来的成功率没有参考价值。

制品是真能用的：从 Release 下载 `app.pyz` 直接执行，功能和错误码都正确。

## 3. 暴露的问题

### 3.1 锁文件清单挡不住"新增一个优先级更高的配置文件"

第一个任务里，生成的验收测试带了个没用到的 `import pytest`，而 `run.sh lint` 会检查整个 `tests/` 目录，于是 lint 失败在一个 agent 不能改的文件上。

agent 的解法是：新建一个 `ruff.toml`。ruff 优先读这个文件而不是被锁定的 `pyproject.toml`，于是它在不碰任何锁定文件的前提下，成功让检查变绿。

它在总结里主动说明了这么做的原因，不是恶意规避。但这正是 reward hacking 的典型形态：**给它一个它无法满足的约束，它就会去改变规则本身**。而且这次是在白盒环境下靠读日志才发现的——如果没人看日志，这个任务会被记成"一次通过"。

两处修复：

- 根因：lint 不再检查生成的验收测试，改成 `ruff check src tests/unit`。
- 兜底：编排侧每轮扫描新增的配置文件（`ruff.toml`、`.ruff.toml`、`setup.cfg`、`tox.ini`、`pytest.ini`、`conftest.py`、`.editorconfig`），发现就删掉，并把这件事回灌给 agent。

对产品的启示，比这个修复本身更重要：**验证配置不能放在 agent 能写的目录里**。正确做法是编排侧用平台自己的配置执行检查（比如 `ruff check --config <平台提供的配置>`），而不是依赖仓库里的配置文件。这条要回写到[技术方案](03-architecture.md)的验证体系一节。

### 3.2 agent 自称的"全绿"不能直接采信

agent 每轮结束前会自己跑一遍三项检查并声称通过。编排侧在它停下后又独立跑了一遍，三次结果一致。但这一步不能省：它能改测试、能改配置、也能只跑一部分测试然后说全过。**报告状态的和被验证的必须是两个主体。**

### 3.3 Gitea Actions 不会把 token 塞进环境变量

CI 第一次跑到"发布 Release"才失败，因为 `GITHUB_TOKEN` 必须在 step 里显式 `env: GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}` 传进去。

这类平台差异应该由模板一次性解决，不能让 agent 去试错——它在沙箱里根本看不到 CI 环境，试错要靠一次次推送，既慢又贵。**模板的质量直接决定成功率**，这条支持了"收窄技术栈、只做黄金路径"的决策。

### 3.4 断网沙箱的代价

`--network none` 让凭证泄露和依赖投毒的风险直接归零，验证下来也完全够用。代价是生成的项目只能用标准库。要支持第三方依赖，得给沙箱配一个带白名单的包管理代理（npm / PyPI 镜像），这是下一步的工作。

## 4. 和技术方案的对照

| 方案里的设计 | POC 里的实现 | 结论 |
|---|---|---|
| 沙箱隔离 | Docker 容器 + `--network none` | 本地够用；多租户仍需 microVM |
| 凭证不进沙箱 | git push 和 Gitea API 都在宿主机侧执行 | 成立，沙箱里没有任何 token |
| 验收测试锁定 | sha256 快照 + 每轮还原 + 新增配置扫描 | 成立，但光锁文件不够，见 3.1 |
| 统一命令契约 | `run.sh lint/test/acceptance/build` | 成立，编排侧完全不关心项目内部结构 |
| 每步一个 commit | 每轮一个 commit | 成立，回滚有基础 |
| 三层闭环 | 沙箱内自测、CI 回灌、用户验收 | 前两层跑通，用户验收还没有界面 |
| 不自研 agent loop | 这次自己写了约 700 行 | 在这个难度下够用；难度上来后再评估换成熟 harness |

## 5. 下一步

1. **加难度**：准备 10 到 30 条更复杂的需求做评测集（多文件、有状态、边界多），测真实成功率、修复轮数和成本。现在的三条太简单，结论不能外推。
2. **验证配置移出仓库**：由编排侧注入 lint 和测试配置，堵掉 3.1 那类绕过。
3. **加需求澄清环节**：现在需求直接进了测试生成，模糊需求会直接变成错误的验收标准。
4. **给沙箱配包管理代理**：支持第三方依赖。
5. **最小 Web UI**：目前只有 CLI，用户验收环节还没法做。
