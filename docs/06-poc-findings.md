# POC 验证结果

> 2026-09-19。代码在 [`../poc/`](../poc/)，这里记录实测数据和暴露出来的问题。

## 1. 产品形态

浏览器打开一个页面，写一句需求，看着大模型在容器里写代码、跑测试，CI 构建部署，最后点链接直接访问做好的网站。用户不用打开 IDE，也不用碰命令行。

全部跑在本机容器里：

| 服务 | 作用 |
|---|---|
| `web` | Web 界面加编排服务，通过宿主机 docker socket 起沙箱 |
| 沙箱 | 每个任务一个，断网，agent 在里面写码跑测试，用完即毁 |
| `gitea` | 代码托管，推送触发 CI |
| `runner` | 跑 Gitea Actions，复用本地沙箱镜像，不拉外网镜像 |
| `pages` | nginx，托管 CI 部署出来的站点 |

CI 和 nginx 共用一个 docker 卷，CI 把 `dist/` 拷进去，nginx 立刻能访问到。这是"CI 完成部署发布"最轻的一种实现。

两条黄金路径：`static-site`（静态网站，部署后可访问）和 `python-cli`（命令行工具，打包成 `.pyz` 发到 Release）。加一条新路径只需要加一个模板目录加一条配置，编排逻辑不动。

**为什么 CI 用 Gitea 不用 GitLab**：GitLab CE 自建要 4GB 内存起步、首次启动好几分钟，而这里只需要验证"推送触发 CI、CI 再部署"。Gitea 加 runner 一共两个容器，内存几百 MB，workflow 语法和 GitHub Actions 兼容，以后迁移成本低。企业私有化场景另说，那时 GitLab 才有意义。

## 2. 实测数据

模型是 DeepSeek `deepseek-flash`，五个任务都是一轮通过，没用上修复轮：

| 任务 | 模板 | 轮次 | 模型调用 | 输入 token（缓存命中） | 成本 | 结果 |
|---|---|---|---|---|---|---|
| 咖啡店单页官网 | static-site | 1 | 13 | 185k（179k） | $0.0127 | 全绿 → CI → 已上线可访问 |
| 个人博客 | static-site | 1 | 17 | 354k（337k） | $0.0208 | 全绿 |
| JSON 格式化校验 | python-cli | 1 | 10 | 41k（38k） | $0.0049 | 全绿 → CI → 制品已发布 |
| 文本词频统计 | python-cli | 1 | 10 | 38k（33k） | $0.0040 | 全绿 |
| CSV 转 JSON | python-cli | 1 | 8 | 27k（24k） | $0.0034 | 全绿 → CI → 制品已发布 |

**多轮迭代**（在已经上线的博客上继续提要求）：

| 轮次 | 要求 | 结果 | 增量成本 |
|---|---|---|---|
| 第 1 轮 | 做一个个人博客 | 上线 | $0.0384 |
| 第 2 轮 | 每篇文章底部加返回首页链接，首页加一句简介 | 改完重新测试、重新部署，地址不变 | $0.0080 |

迭代走的是同一个工作区、同一个仓库、同一个站点地址。这次的新要求会生成一份新的验收测试追加进去，**第一轮的验收测试继续跑**——改新功能把老功能改坏了会被当场拦住。增量成本只有首次的五分之一，因为不用重新搭架子。

观察：

- **单任务成本一到两分钱**。网站类任务比命令行工具贵三到五倍，因为文件多、内容长。按这个价格，跑一个 30 条样本的评测集不到一块钱，成本完全不构成障碍。
- **缓存命中率 88% 到 96%**。agent 每轮重发完整上下文，但命中缓存的部分单价只有 miss 的 1/50，所以实际花费远低于按 token 数的直觉估算。
- **产出的东西像个真东西**。咖啡店官网有自写的 SVG logo、菜单分类切换、吸顶导航和真实文案；博客自己写了个模板引擎，用 JSON 存文章、渲染出首页和五篇文章页。都没有用任何外部资源——沙箱断网逼出来的。
- **五个任务都一轮通过**，说明这个难度对模型来说偏简单，测不出真实成功率。下一步必须加难度。

## 3. 暴露的问题

### 3.1 锁文件清单挡不住"新增一个优先级更高的配置文件"

第一个命令行任务里，生成的验收测试带了个没用到的 `import pytest`，而 lint 检查整个 `tests/` 目录，于是 lint 失败在一个 agent 不能改的文件上。

agent 的解法是新建一个 `ruff.toml`。ruff 优先读它而不是被锁定的 `pyproject.toml`，于是它在不碰任何锁定文件的前提下让检查变绿了。

它在总结里主动说明了原因，不是恶意。但这正是 reward hacking 的典型形态：**给它一个无法满足的约束，它就去改变规则本身**。而且这次是靠读日志才发现的，否则这个任务会被记成"一次通过"。

修了两处：根因上 lint 不再检查生成的验收测试；兜底上编排侧每轮扫描并删除新增的配置文件（`ruff.toml`、`setup.cfg`、`tox.ini`、`pytest.ini`、`conftest.py` 等）。

对产品的启示比修复本身更重要：**验证配置不能放在 agent 能写的目录里**，应该由编排侧用平台自己的配置执行检查。

### 3.2 agent 自称的"全绿"不能直接采信

agent 每轮结束前会自己跑一遍三项检查并声称通过。编排侧在它停下后又独立跑了一遍，结果一致。但这一步不能省：它能改测试、能改配置，也能只跑一部分测试然后说全过。**报告状态的和做验证的必须是两个主体。**

### 3.3 模板的小毛病会被 agent 用"绕过"来消化

静态网站模板的 `run.sh` 我漏了可执行位，agent 遇到 `Permission denied` 之后自己 `chmod +x` 接着干，任务照样绿。听上去是韧性好，其实是坏消息：**模板的缺陷被掩盖了**，而且每次都要浪费几轮去绕，CI 里还会再挂一次（CI 用的是仓库里的文件）。

这类问题应该由模板一次性解决。同理还有 Gitea Actions 不会把 `GITHUB_TOKEN` 注入环境变量、必须在 step 里显式传——agent 在沙箱里看不到 CI 环境，试错只能靠一次次推送，既慢又贵。**模板质量直接决定成功率和成本**，这条支持了"收窄技术栈、只做黄金路径"的决策。

### 3.4 断网沙箱的代价

`--network none` 让凭证泄露和依赖投毒的风险直接归零，验证下来完全够用，还逼出了"不依赖 CDN"的站点。代价是只能用标准库、只能手写样式。要支持第三方依赖或 npm 生态，得给沙箱配一个带白名单的包管理代理。

### 3.5 测试全绿，线上照样 404

第一版把每个站点部署在 `localhost:8081/<项目名>/` 这个子目录下。生成的博客用的是绝对路径链接（`/about.html`、`/posts/xxx.html`），而验收测试里站点跑在本地服务器的根目录——测试全绿，线上却在子目录，绝对路径全部指到了 nginx 的根目录，文章详情页无一例外 404。

用户点开"已上线"的链接，看到的是坏的。**只要测试环境和生产环境有一点不一致，测试通过就不代表线上能用**，而这套系统里用户是没有能力自己发现和修复的。

修法不是要求模型改用相对路径（那是把问题推给模型的自觉），而是让两边环境一致：每个站点挂在自己的子域名根目录下（`http://<项目名>.localhost:8081/`），和验收测试里的本地服务器形态完全相同。

启示：**预览、验收测试、生产必须是同一种路径形态**，差一点都会漏过去。这条要写进技术方案的验证体系一节。

### 3.6 编排服务进了容器之后，多了两个坑

- **路径**：编排服务在容器里，起沙箱时 `-v` 的源路径必须是宿主机上的真实路径，不是容器内的路径。多传一个 `WORKSPACES_HOST_DIR` 解决。
- **地址**：服务之间要用 `http://gitea:3000`，给用户点的链接要用 `http://localhost:3000`。两套地址必须分开配，否则要么服务连不上，要么用户点开是死链。

另外 8080 端口被 Docker Desktop 自己占了，站点服务换到了 8081——本地环境的端口冲突，部署到别的机器上要重新确认。

## 4. 和技术方案的对照

| 方案里的设计 | POC 里的实现 | 结论 |
|---|---|---|
| 沙箱隔离 | Docker 容器加 `--network none` | 本地够用；多租户仍需 microVM |
| 凭证不进沙箱 | git push 和 Gitea API 都在编排侧执行 | 成立，沙箱里没有任何 token |
| 验收测试锁定 | sha256 快照、每轮还原、扫描新增配置 | 成立，但光锁文件不够，见 3.1 |
| 统一命令契约 | `run.sh build/lint/test/acceptance` | 成立，编排侧完全不关心项目内部结构 |
| 每步一个 commit | 每轮一个 commit | 成立，回滚有基础 |
| 三层闭环 | 沙箱内自测、CI 回灌、用户验收 | 三层都通了，但用户验收还只是"点开看"，没有逐条确认验收标准 |
| CI 完成部署发布 | CI 写共享卷，nginx 直接托管 | 成立，而且很轻 |
| 不自研 agent loop | 这次自己写了几百行 | 在这个难度下够用；难度上来后再评估换成熟 harness |

## 5. 下一步

1. **加难度**：准备 10 到 30 条更复杂的需求做评测集（多页面、有交互、有数据、边界多），测真实成功率、修复轮数和成本。现在五条太简单，结论不能外推。
2. **需求澄清环节**：现在需求直接进了测试生成，模糊需求会直接变成错误的验收标准。
3. **在界面上做迭代**：目前每次都是新建项目，不能基于已有站点改需求。这是产品化最该补的一环。
4. **验收标准可视化**：把生成的验收标准在界面上逐条展示，让用户确认后再开工，完成后逐条对照。
5. **验证配置移出仓库**，堵掉 3.1 那类绕过。
6. **沙箱包管理代理**，支持第三方依赖。
