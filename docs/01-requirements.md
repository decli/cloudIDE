# 需求说明

> 状态：草案 v0.1（2026-09-17）。标注"待确认"的内容是基于构想的假设，需要产品负责人拍板。

## 1. 背景与愿景

一个有想法、但不会写代码或不想搭环境的人，今天要把小项目做出来并上线，仍然要经历选技术栈、搭环境、写代码、调试、配置 CI、部署这一整套流程。大模型编码 agent 已经能完成其中大部分步骤。

cloudIDE 的愿景：**用户只负责说清楚要什么、判断做得对不对；从写代码到发布上线，全部由平台完成。**

## 2. 目标用户（待确认）

| 画像 | 典型需求 | 付费意愿 | 竞争强度 | 备注 |
|---|---|---|---|---|
| A. 非技术个人、小团队 | 落地页、作品集、小工具、小游戏 | 低到中 | 很高（Lovable、Bolt、v0、Replit 等） | 获客容易，留存和毛利难；多数人没有 GitHub 账号 |
| B. 企业里的业务、产品、运营人员 | 活动页、内部工具、数据看板、自动化脚本 | 中到高（企业买单） | 中（私有化场景海外产品进不来） | 需要接入企业 GitLab、审计、国产模型 |
| C. 开发者 | 把 issue 异步委派给 agent，产出 PR | 中 | 很高（Copilot、Codex、Claude Code、Jules） | 与模型厂商正面竞争，不建议作为首选 |

初步建议：用 A 验证核心链路，把 B 作为商业化方向（见[决策记录](05-decisions.md) Q-02）。

## 3. 核心用户旅程

1. **描述需求**：用自然语言描述要做什么，可以附参考链接、截图和文案。
2. **澄清**：平台只问少数关键问题，比如目标用户、核心功能、风格、是否需要登录或存数据。
3. **确认规格**：平台给出规格说明、验收标准和可点击的原型，用户确认或修改。
4. **自动开发**：平台在沙箱里编码、测试、修复。用户能看到计划、进度、日志和 diff，可以随时暂停、补充说明或取消。
5. **预览验收**：用户在预览环境里试用，对照验收标准逐条确认；不满意就用自然语言提修改意见。
6. **发布**：推送到用户的 GitHub / GitLab 仓库，由 CI 构建并发布到 Pages，或生成 Release 制品。
7. **迭代**：上线后继续提需求，平台增量修改（新需求 → 规格 diff → 代码 diff）。
8. **接管（逃生舱）**：任何时候都能导出代码、在 Codespaces 或本地 IDE 打开，或申请工程师介入。

## 4. 功能需求

优先级：P0 = MVP 必须；P1 = 第二阶段；P2 = 之后。

### 4.1 需求与规格

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-01 | 对话式输入需求，支持附图片和链接 | P0 |
| FR-02 | 澄清问答：一次最多问 3–5 个关键问题，可跳过；跳过时按默认假设继续，并在规格里写明 | P0 |
| FR-03 | 生成规格说明：功能列表、页面或模块、数据、非目标 | P0 |
| FR-04 | 生成验收标准，用户确认后锁定，作为自动化验收测试的来源 | P0 |
| FR-05 | 生成可点击的原型或线框，确认后再开始编码 | P1 |
| FR-06 | 规格版本化，修改需求时展示规格 diff | P1 |

### 4.2 开发执行

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-10 | 按项目类型选模板初始化仓库（MVP 只有"前端应用 → Pages"一种） | P0 |
| FR-11 | 在隔离沙箱中执行"计划 → 编码 → 测试 → 修复"循环，直到验收测试通过或触达上限 | P0 |
| FR-12 | 实时展示当前计划、步骤进度、终端日志、文件 diff、已花费成本 | P0 |
| FR-13 | 用户可以暂停、补充指令、取消任务 | P0 |
| FR-14 | 每一步产生 git commit，可以回滚到任一测试通过的版本 | P0 |
| FR-15 | 触达次数或预算上限时停下，给出看得懂的阻塞原因和建议操作 | P0 |
| FR-16 | 卡住时自动降级：换更强的模型、提高推理强度、拆分任务、回滚后重试 | P1 |

### 4.3 验证与预览

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-20 | 静态检查：lint、类型检查、构建 | P0 |
| FR-21 | 验收测试（来自 FR-04）由独立流程生成，编码 agent 无权修改 | P0 |
| FR-22 | 每个任务有一个需要登录才能访问的预览 URL | P0 |
| FR-23 | E2E 测试加关键页面截图，由多模态模型对照验收标准检查 | P1 |
| FR-24 | 独立评审 agent 审查 diff：正确性、安全、可维护性 | P1 |
| FR-25 | 安全扫描：密钥泄露、依赖漏洞、常见漏洞模式 | P1 |

### 4.4 发布与 CI/CD

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-30 | 通过 GitHub App 授权，在用户账号下从模板创建仓库，推送分支，创建并合并 PR | P0 |
| FR-31 | 模板内置 GitHub Actions 工作流，合并后自动发布到 GitHub Pages | P0 |
| FR-32 | 监听 CI 结果，失败时把日志回灌给 agent 自动修复（有次数上限） | P0 |

| FR-34 | 支持 GitLab：OAuth 或 Project Access Token、GitLab CI、GitLab Pages | P1 |
| FR-35 | 支持更多发布目标：Vercel、Cloudflare、国内云静态托管 | P2 |

### 4.5 账户、计费与管理

## 5. 非功能需求

| 编号 | 类别 | 要求 |
|---|---|---|
| NFR-01 | 隔离 | 用户代码只在 microVM 或 gVisor 级别隔离的沙箱里运行；沙箱之间、沙箱与平台之间网络隔离 |
| NFR-02 | 出网控制 | 沙箱默认禁止出网，只放行包管理镜像、模型网关、Git 代理等白名单；禁止访问内网和云元数据地址 |
| NFR-03 | 凭证 | Git token 和用户密钥不进入沙箱和模型上下文，由代理在出口注入；token 最小权限、短时有效 |
| NFR-04 | 可恢复 | 任务流程持久化，平台重启或沙箱故障后能从最近的检查点继续 |
| NFR-05 | 速度 | 沙箱就绪 P95 ≤ 5 秒；从确认规格到首个预览可见，中位数 ≤ 10 分钟（建议初值，待校准） |
| NFR-06 | 成本 | 每个任务有硬预算；单项目首版中位成本 ≤ $10（建议初值，待校准） |
| NFR-07 | 可观测 | 每个任务都能回放完整轨迹：模型调用、工具调用、命令输出、成本 |
| NFR-08 | 可移植 | 模型经统一网关调用，可以切换供应商；沙箱层可以替换 |
| NFR-09 | 防滥用 | 对生成内容和发布的站点做风险检测（钓鱼、诈骗、恶意代码）；发布到用户自己的账号 |
| NFR-10 | 合规 | 面向国内时：使用已备案模型，完成生成式 AI 服务备案或登记，数据境内存储 |

## 6. MVP 范围

**包含**：第 4 节中所有 P0 项。只支持一个模板：前端单页应用（Vite + React + TypeScript）→ GitHub Pages。

**不包含**：
- 后端服务、数据库、登录系统
- 移动 App、桌面应用、代码签名
- 导入和改造已有代码库
- GitLab、私有化部署
- 多人协作

## 7. 成功指标

| 指标 | 定义 |
|---|---|
| 端到端交付成功率 | 没有人工介入，从需求到上线并通过用户验收的任务占比 |
| 单次成功交付成本 | 总成本（token + 沙箱 + CI）÷ 成功交付数，失败任务的成本也算在内 |
| 首次上线耗时 | 从确认规格到 Pages 可以访问的时间 |
| 二次迭代率 | 首版上线后 7 天内再次提出修改的项目占比 |
| 卡死率 | 触达上限、需要人工处理或被放弃的任务占比 |
