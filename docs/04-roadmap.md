# 路线图

> 时间是粗估，假设 2–3 名全职工程师。退出标准里的数值都是建议初值，Phase 0 结束后根据数据校准。

## Phase 0：验证（2–3 周）

目标：先不做产品界面，只回答两个问题：黄金路径能不能稳定跑通？要花多少钱？

- 收集 30 条真实的前端应用需求样本，写清验收标准，作为评测集。
- 做一个模板仓库：Vite + React + TypeScript → GitHub Pages，包含 AGENTS.md、命令契约和 CI。
- 写脚本驱动整条链路：选定的 harness 加沙箱 → 逐条执行样本 → 推送 → CI → Pages。
- 记录每条样本的结果、轮数、token、耗时和失败原因。
- 验证 GitHub App 的建仓、降权推送、启用 Pages 等关键行为。

退出标准：
- 端到端成功率（无人工介入、验收标准全部满足）≥ 60%
- 单项目中位成本 ≤ $10
- 找出前 3 类失败原因，并有对策

## Phase 1：MVP（4–6 周）

目标：让外部种子用户真正用上黄金路径。

- Web 工作台：需求对话、澄清、规格确认、进度与日志、预览、验收、发布。
- 编排服务（Temporal）、任务状态机、上限与预算。
- GitHub App 集成、从模板生成仓库、CI 结果回灌。
- 锁定的验收测试、预览环境、回滚。
- 用量计量和基础管理后台。
- 安全基线：沙箱隔离、出网白名单、凭证代理、预览鉴权。

退出标准：
- 20–50 名种子用户，端到端成功率 ≥ 70%
- 首次上线耗时中位数 ≤ 30 分钟
- 7 天二次迭代率 ≥ 30%

## Phase 2：可用性与商业化（6–8 周）

- 原型确认、规格版本与 diff、卡住时的自动降级。
- E2E 截图检查、独立评审 agent、安全扫描。
- 计费（订阅加 credit，或按交付计费）和防滥用。
- 第二个模板，根据 Phase 1 数据在"全栈（借助 BaaS）"和"CLI → Releases"之间选。

## Phase 3：扩展（按决策选方向）

- **企业方向**：GitLab 支持、私有化部署、SSO、审计、国产模型适配。
- **垂直方向**：深耕一个场景的模板和组件库。
- **发布目标**：Vercel、Cloudflare、国内云静态托管。

## 核心指标

| 指标 | 定义 | 为什么重要 |
|---|---|---|
| 端到端交付成功率 | 无人工介入上线并通过验收的任务占比 | 决定产品能不能成立 |
| 单次成功交付成本 | 总成本 ÷ 成功交付数，含失败任务 | 决定毛利 |
| 首次上线耗时 | 从确认规格到上线 | 核心体验 |
| 二次迭代率 | 7 天内再次修改的项目占比 | 留存的先行指标 |
| 卡死率 | 触达上限、需要人工或被放弃的任务占比 | 体验底线 |

## 主要风险与应对

| 风险 | 触发信号 | 应对 |
|---|---|---|
| 成功率上不去 | Phase 0 成功率 < 60% | 进一步收窄需求范围，加强模板和验收测试；考虑"AI 加人工兜底"模式 |
| 成本过高 | 中位成本 > $10 | 缓存、推理强度分级、模型分层；调整计费模式 |
| 同质化 | 种子用户拿去和 Lovable 等比较后流失 | 尽早转向企业私有化或垂直场景 |
| 合规 | 决定面向国内 | 提前完成模型选型和备案规划 |
